# 04. フリック入力仕様

本作で最重要の実装領域。原文 §18 の開発優先順位でも1位に置かれている。

## 4.1 操作モデル

**射出領域内ならどこでもフリック可能。ドラッグ中カードは指に追従しない。**

```text
PointerDown（射出領域内）
    ↓
待機中の投げカードが、触れた X 座標へ即座にスナップ
（Y は射出ライン固定、X は安全マージン内にクランプ）
    ↓
PointerMove 履歴を記録（t, x, y）
    ↓
PointerUp
    ↓
直近 INPUT_SAMPLE_WINDOW_MS の履歴から速度・方向を推定
    ↓
正規化・クランプ
    ↓
Matter.js の Body へ初速を設定
```

### 設計判断の根拠

| 判断 | 根拠 |
|---|---|
| 射出領域内ならどこでもよい | カード上のみに限定すると空振り（タップが判定外）が発生し、「入力したのに何も起きない」という最悪のフィードバックになる |
| カードは指に追従しない | 追従させると実質スリングショット式になり、原文 §7 が明示的に否定した方式に近づく。また射出位置が可変になり「この距離ならこの強さ」の学習が成立しにくくなる |
| 触れた X にスナップする | 指とカードが離れた場所にあると「直接弾いている」身体感覚が失われる。X のみスナップすることで、視覚的な一致を保ちつつ射出距離（Y）は常に一定に保たれる |
| Y はスナップしない | Y が変わるとターゲットまでの距離が毎回変わり、原文 §19「数回遊ぶと停止距離を学習できるか」が成立しなくなる |

## 4.2 受理条件

PointerDown を投擲の開始として受理する条件：

| 条件 | 内容 |
|---|---|
| 状態 | `phase === 'ready'` であること |
| 位置 | 論理座標に変換した Y が `layout.launchZoneTop` 以上であること |
| 手札 | `hand > 0` であること |
| ポインタ | 既に追跡中の `pointerId` がないこと（マルチタッチは最初の1本のみ受理） |

受理しない PointerDown は完全に無視する（デバッグパネル上のタッチは `ui` 側で `stopPropagation` して分離する）。

## 4.3 サンプル履歴

`input/history.ts` はリングバッファで PointerMove を記録する。

```ts
interface SampleHistory {
  push(t: number, x: number, y: number): void;
  /** 直近 windowMs 以内のサンプルを古い順に返す */
  recent(nowMs: number, windowMs: number): readonly PointerSample[];
  clear(): void;
}
```

| パラメータ | 初期値 | 意味 |
|---|---:|---|
| `MAX_HISTORY` | 32 | リングバッファのサイズ |
| `INPUT_SAMPLE_WINDOW_MS` | 80 | 速度推定に使う直近の時間窓 |
| `MIN_SAMPLES` | 3 | 回帰に必要な最小サンプル数 |

記録する座標は**論理座標に変換済みの値**とする。これにより DPR や画面サイズの差が速度推定に入り込まない（原文 §7「画面サイズ差・DPR差の吸収」）。

`getCoalescedEvents()` が利用可能な環境では、それを用いて高頻度のサンプルを取得する。これにより 120Hz 端末での推定精度が上がる。

```ts
function onPointerMove(e: PointerEvent): void {
  const events = e.getCoalescedEvents?.() ?? [e];
  for (const ev of events) {
    const p = screenToLogical({ x: ev.clientX, y: ev.clientY }, layout);
    history.push(ev.timeStamp, p.x, p.y);
  }
}
```

## 4.4 速度推定アルゴリズム

**線形回帰 ＋ ピーク速度ブレンド**を採用する。

### 手順

```text
[1] 直近 INPUT_SAMPLE_WINDOW_MS のサンプルを取り出す
      ↓ サンプル数 < MIN_SAMPLES なら null（投擲不成立）
[2] x(t), y(t) をそれぞれ最小二乗法で1次回帰し、傾きを求める
      v_reg = (slope_x, slope_y)   単位: 論理px/ms
      ↓
[3] 連続するサンプル間の瞬間速度の最大値（ノルム最大のもの）を求める
      v_peak                        単位: 論理px/ms
      ↓
[4] ブレンド
      v_blend = v_reg × (1 - PEAK_BLEND) + v_peak × PEAK_BLEND
      ↓
[5] 初速へ変換・クランプ
      speed = |v_blend| × FLICK_POWER
      speed < MIN_FLICK_SPEED → 投擲不成立（null）
      speed > MAX_FLICK_SPEED → MAX_FLICK_SPEED にクランプ
      ↓
[6] 方向は v_blend を正規化したものを使う
      launch = normalize(v_blend) × speed
```

### 線形回帰の式

時間窓内のサンプル `(t_i, x_i)` について、`t` の平均を引いて数値安定性を確保したうえで：

```text
slope_x = Σ((t_i - t̄)(x_i - x̄)) / Σ((t_i - t̄)²)
```

分母が 0（全サンプルが同一時刻）の場合は `null` を返す。

### ピーク速度ブレンドの意図

人間は指を離す直前に無意識に減速する。時間窓内の回帰だけを使うと、この減速を拾って「思ったより弱く飛ぶ」現象が起きる。一方でピーク速度だけを使うと、単一のノイズサンプルがそのまま最大速度になり、意図しない強い射出が混ざる。

両者をブレンドし、**ブレンド比 `PEAK_BLEND` をデバッグUIで実機調整可能にする**ことで、この主観的な問題をコード編集なしに詰められるようにする（原文 §17）。

| パラメータ | 初期値 | 範囲 | 意味 |
|---|---:|---|---|
| `PEAK_BLEND` | 0.35 | 0.0 〜 1.0 | 0 なら回帰のみ、1 ならピークのみ |

## 4.5 初速へのマッピング

**線形 ＋ ハードクランプ**を採用する。

```text
speed = clamp(|v_input| × FLICK_POWER, MIN_FLICK_SPEED, MAX_FLICK_SPEED)
```

| パラメータ | 初期値 | 単位 | 意味 |
|---|---:|---|---|
| `FLICK_POWER` | 6.0 | (論理px/step) / (論理px/ms) | 指の速度を初速に変換する係数 |
| `MIN_FLICK_SPEED` | 8.0 | 論理px/step | これ未満は誤タップとみなし投擲不成立 |
| `MAX_FLICK_SPEED` | 62.0 | 論理px/step | 上限 |

### 線形を選んだ根拠

ガンマカーブ等の非線形マッピングは弱入力域の解像度を上げられるが、「2倍の速さで振れば約2倍飛ぶ」という直感が崩れる。原文 §2 の「フリックの強さと方向を**身体で覚え**る」および §20「入力と結果の対応を一貫させる」を最優先するため、線形とする。

### MAX の決め方

上限に頻繁に当たると「強く振っても同じ」という天井を感じてゲームが壊れる。`MAX_FLICK_SPEED` は**盤面を縦断して少し余る速度**に設定し、通常のプレイでは到達しないようにする。

減速モデル（[05-physics.md](./05-physics.md)）から、初速 `v0` の総移動距離は概ね `v0 / FRICTION_AIR` である。盤面高さ約1800論理px を飛ぶには `v0 ≈ 1800 × 0.028 = 50.4`。上限 62 はこれに約24%の余裕を持たせた値であり、「全力で振れば場外に飛び出す」ことが可能な設定になっている。これは決定8（上端の場外ロスト）と対になり、**強すぎるフリックへのペナルティを物理的に成立させる**。

## 4.6 投擲の成立と不成立

| 結果 | 条件 | 手札 | 状態遷移 |
|---|---|---|---|
| 成立 | 推定速度 ≧ `MIN_FLICK_SPEED` | −1 | `aiming` → `flying` |
| 不成立（弱すぎ） | 推定速度 < `MIN_FLICK_SPEED` | 変化なし | `aiming` → `ready` |
| 不成立（サンプル不足） | サンプル数 < `MIN_SAMPLES` | 変化なし | `aiming` → `ready` |
| 不成立（キャンセル） | `pointercancel` 発生 | 変化なし | `aiming` → `ready` |

**投擲不成立で手札を減らさない**ことは重要である。タップしただけでカードを1枚失うのは、原文 §20「操作ミスとゲーム側の不確実性を混同させない」に反する。

## 4.7 実機チューニングの指針

原文 §18 の優先順位1位「フリック入力精度」を詰めるため、デバッグUI（[08-render-ui.md](./08-render-ui.md)）には以下を必ず露出させる。

- `FLICK_POWER` / `MIN_FLICK_SPEED` / `MAX_FLICK_SPEED`
- `INPUT_SAMPLE_WINDOW_MS` / `PEAK_BLEND`
- 直前の投擲の推定値の表示（指の速度、回帰値、ピーク値、最終初速、クランプされたか否か）

最後の「クランプされたか否か」の表示は、チューニング時に「上限に当たり続けていて調整が効いていない」という状況を即座に発見するために不可欠である。
