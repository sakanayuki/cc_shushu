# 12. 実装ロードマップ

## 12.1 方針

原文 §18 の開発優先順位に従う。

> ゲームルールを増やすより先に、FLICK → SLIDE → COLLISION → STOP の手触りを完成させる。

各マイルストーンは**それ単体で動作し、触って評価できる状態**を目指す。動かない中間状態を長く持たない。

## 12.2 マイルストーン

### M0 — 骨格とデプロイ配線

**目的**: 「push したら公開される」を最初に通しておく。後回しにすると、完成間際にデプロイで詰まる。

| 作業 | 完了条件 |
|---|---|
| `package.json` / `tsconfig.json` / `vite.config.ts` / ESLint 設定 | `npm run typecheck` と `npm run lint` が通る |
| `index.html` と Canvas の初期化 | 画面が単色で塗りつぶされる |
| `.github/workflows/deploy.yml` | Actions が緑になる |
| GitHub Pages の Source を GitHub Actions に設定 | 公開URLで単色の画面が見える |

**検証**: `https://sakanayuki.github.io/cc_shushu/` にスマホでアクセスし、全画面が塗られていること。

### M1 — 座標系と描画

| 作業 | 完了条件 |
|---|---|
| `config/params.ts` / `config/layout.ts` | 全パラメータが型付きで定義される |
| `core/coords.ts` | 往復変換のテストが通る |
| `render/canvas.ts` / `theme.ts` / `skins/defaultSkin.ts` | 盤面の枠・ロストライン・射出ラインが描かれる |
| 固定のカードをハードコードして描画 | 置きカードと投げカードが正しい位置と大きさで見える |

**検証**: 複数の端末サイズ（開発者ツールのデバイスエミュレーション）で、レターボックスが正しく出ること。

### M2 — フリック入力（★最重要）

原文 §18 の優先度1位。ここに最も時間をかける。

| 作業 | 完了条件 |
|---|---|
| `input/history.ts` / `input/pointer.ts` | PointerMove が論理座標で記録される |
| `core/flick.ts` | 速度推定のテストが通る |
| `physics/world.ts` / `bodies.ts` / `stepper.ts` | カードが初速を受けて滑る |
| `physics/settle.ts` | 停止判定が機能する |
| デバッグパネル（FLICK セクションのみ） | 実機でパラメータを変えられる |

**検証**: 実機で50回以上投げ、以下を確認する。

- 狙った方向へ飛ぶか
- 強弱を意図的に使い分けられるか
- 「強すぎた」「弱すぎた」が自分の責任だと感じられるか

**この段階で手触りが悪ければ、先に進まずここを詰める。** 判定やUIを足しても手触りは改善しない。

### M3 — 摩擦・停止距離・衝突

| 作業 | 完了条件 |
|---|---|
| 壁の実装と上端の場外ロスト | 上端を越えたカードが消える |
| 複数カードの同時存在と衝突 | 投げカード同士が衝突して双方が動く |
| デバッグパネル（PHYSICS セクション） | 実機で摩擦と反発を調整できる |

**検証**: 数回遊んで停止距離を学習できるか。カードを押して動かす操作が意図通りに行えるか。

### M4 — 判定と得点

| 作業 | 完了条件 |
|---|---|
| `core/geometry.ts` | レンズ面積のテストが全て通る |
| `core/rng.ts` / `core/board.ts` | 配置制約のテストが通る。`?seed=` が機能する |
| `core/resolve.ts` | 決着処理のテストが全て通る |
| 被覆率の表示 | 停止後に各カードの上に `48%` が出る |
| 獲得・回収・補充 | 過半数を超えたカードが消え、投げカードが手札に戻り、新カードが出る |

**検証**: 「あと1枚寄せれば取れる」という状況を意図的に作り、実際に取れること。

### M5 — 手札制とゲームループ

| 作業 | 完了条件 |
|---|---|
| `core/machine.ts` | 状態遷移が仕様通りに動く |
| `ui/hud.ts` | 手札枚数と累計得点が見える |
| `ui/result.ts` | 手札0で終了し、Retry で再開できる |
| ベストスコアの `localStorage` 保存 | リロードしても残る |

### M6 — 仕上げ

| 作業 | 完了条件 |
|---|---|
| 得点ポップ・回収アニメ・空振りフェード | 何が起きたか目で追える |

| チューニング（[09-tuning.md](./09-tuning.md) 9.4節の手順） | 各パラメータの根拠を 9.3 節に記録 |

**検証**: 原文 §19 の確認項目8つをすべて満たすか。初見の人に遊んでもらう。

## 12.3 実装順序の原則

```text
[1] デプロイ配線を最初に通す        M0
        ↓
[2] 手触りを完成させる              M2 → M3
        ↓
[3] ルールを載せる                  M4 → M5
        ↓
[4] 理解を助ける表示を足す          M6
```

**M2 と M3 が本体である。** M4 以降は M2/M3 が成立していることを前提に、その上へ意味を載せる作業にすぎない。手触りが弱いまま M4 に進むと、ルールで面白さを補おうとして原文 §20「PoCでは足さない」に反する方向へ引きずられる。

## 12.4 各マイルストーンでの判断基準

M2 完了時点で、以下を自問する。

> **カードを投げて滑らせて止めるだけの状態で、10回以上続けて投げたくなるか。**

ここで「ならない」なら、M4 以降に進んでも面白くならない。物理パラメータ、入力推定、あるいは論理座標系のスケールのいずれかに問題がある。デバッグUIで詰め直す。

M5 完了時点で、原文 §19 の最重要評価を自問する。

> **何も追加しなくても、もう一度フリックしたくなるか。**

## 12.5 将来の拡張候補（PoC 範囲外）

以下は PoC が成立した後に検討する。**PoC 段階では一切実装しない。**

| 候補 | 原文での位置づけ | 備考 |
|---|---|---|
| スピン・カーブ | §13 | 円形剛体は回転だけでは曲がらないため、角速度に応じた横力の付加が必要 |
| ランキング | §16 実装しない | 静的ホスティングのため外部APIが必要 |
| 障害物・バンパー | §16 実装しない | §20「フリック操作を面白くするか」で採否を判断する |
| カードデザインの刷新 | 決定25 | `theme.ts` と `CardSkin` の差し替えのみで完結する設計になっている |
| 難易度カーブ | — | 獲得数に応じてスロット構成を変える等。まず基本が成立してから |

## 12.6 設計変更時の手順

実装中に設計と異なる判断が必要になった場合、以下を守る。

1. 該当する章のドキュメントを**先に**更新する
2. [README.md](./README.md) の決定事項サマリを更新する
3. 原文コンセプト（[00-source-design.md](./00-source-design.md)）からの逸脱であれば、[01-overview.md](./01-overview.md) 1.4節の変更点表に追記する
4. 変更の**理由**を必ず書く

理由を失った決定は、次に触る人（半年後の自分を含む）が安易に戻してしまう。本設計書が30件の決定について逐一根拠を記録しているのは、そのためである。
